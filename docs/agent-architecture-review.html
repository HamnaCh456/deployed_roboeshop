First, the word "agent"

The proposal uses it in two unrelated senses, and mixing them up will cost marks in the defence.

SenseWhereWhat it really is
Scraping agentProposal §5 — "automated web scraping agents … such as Scrapy"A crawler. No AI. Deterministic CSS and regex extraction. Already built — scraper/
LLM agentProposal §10 — "a dedicated AI chatbot"An LLM given a role, a prompt and tools, wired into a graph. This is what the NVIDIA repo is

Everything in Part A is about the second sense.

Part A

How the blueprint works

Read from the source rather than from its README.

A1 It is not one program; it is six containers

docker-compose.yaml brings up seven services. The agents live in exactly one of them.

ServicePortRoleSize
chain-server8009All five agents, plus the graph that routes between them~2,100 LOC
catalog-retriever8010Embeds the product CSV into Milvus, answers similarity queries~1,150 LOC
memory-retriever8011SQLite store of per-user conversation context and cart~225 LOC
rails8012NeMo Guardrails — input and output safety filter~150 LOC
milvus + etcd + minio19530Vector database and its two dependenciesthird-party
frontend—React UI — the one already copied into ui/—
nginx3000Reverse proxy—

The line to notice in their README is the hardware requirement:

Hardware: 4x H100 GPUs (preferred) or 4x A100 GPUs (minimum) for local deployment

That is because the blueprint runs three NVIDIA NIM models locally: a 120-billion-parameter LLM (nvidia/nemotron-3-super-120b-a12b), a text embedding model (nv-embedqa-e5-v5), and an image embedding model (nvclip). Four H100s is roughly US$100,000+ of hardware, or about $12–15/hour rented. A config-build.yaml override points at NVIDIA's hosted API instead — that path needs no GPU, and it is the only one relevant to us.

A2 The five agents

All five live in chain_server/src/. Each is a small Python class with an invoke(state) method. There is no autonomous agent loop anywhere — no agent decides to call another agent. A fixed graph decides.

FileClassLLM?What it does
planner.pyPlannerAgent1 callReads the query, outputs one word: cart, retriever, or chatter
retriever.pyRetrieverAgent1 callTurns "dresses under $100" into {entities, categories, filters}, then calls the catalog service
cart.pyCartAgent1 callTool-calls add / remove / view / total; resolves fuzzy names to real catalog rows
chatter.pyChatterAgent1 streamingWrites the answer the user sees. Always runs, always last
summarizer.pySummaryAgentsometimesCompresses the conversation past 16,384 chars, then persists it

So a single user message costs two to three LLM calls, not one.

A3 The State object — what flows between agents

Everything is one Pydantic model, in chain_server/src/agenttypes.py:

class State(BaseModel):
    user_id: int
    query: str                   # what the user typed
    context: str                 # summarised history of the conversation
    cart: Cart                   # authoritative cart contents
    response: str                # written by whichever specialist ran
    image: str                   # base64, if a photo was uploaded
    retrieved: Dict[str, str]    # {product_name: image_url} — this turn only
    next_agent: str              # set by the planner
    guardrails: bool
    timings: Dict[str, float]    # every step is timed

Two fields carry most of the design weight. retrieved is wiped and refilled every turn — it is the allowlist of products the final responder may name, and it is how they stop the model inventing stock. context is a summary, not a transcript, and it is explicitly labelled "not authoritative" when handed on.

Three things in that diagram are worth stealing outright:

  1. The planner and the safety check run in parallel. memory_node fans out to both, and the graph joins them at check_rail_node. The safety check is therefore free in wall-clock terms.
  2. Exactly one specialist runs per turn. It is a router, not a debate between agents.
  3. The chatter always runs last, and is the only agent that talks to the user. Specialists produce data; the chatter produces prose.

A5 Agent by agent

The Planner — a one-word classifier

It sends the query plus a ~50-line routing prompt at temperature=0.0, max_tokens=100 and expects a single token back. Everything around that call is defensive:

mappings = {"search": "retriever", "cart_node": "cart",
            "product_finder": "retriever", "general": "chatter", ...}
normalized = mappings.get(agent_name, agent_name)
if normalized not in self.agent_choices:
    logger.warning(f"Invalid agent choice '{normalized}', defaulting to 'chatter'")
    return "chatter"

If the model returns garbage, or the call throws, it falls back to chatter. The system degrades to a plain chatbot rather than crashing. The planner is also given the query without conversation context — their comment says this is "to avoid routing bias."

The routing prompt encodes one genuinely subtle distinction, and our domain has the same problem:

  • "show me dresses under $100" → search — there is a product type
  • "show me anything under $100" → chatter — constraint only, so ask a clarifying question instead of guessing

The Retriever — natural language into a structured query

The most instructive file in the repo. It does not throw the user's sentence at a vector database. It first runs an LLM extraction step with a forced tool schema, producing:

{ "search_entities": ["earrings"], "category_one": "earrings",
  "min_price": null, "max_price": 200 }

The prompt for that step is ~90 lines of ordered decision logic — attribute follow-up, then new product type, then open-ended browse — with worked examples for each. Then the code, not the model, cleans up after it:

  • _sanitize_categories() drops any category the model invented that is not in the configured allowlist.
  • _normalize_filters() throws away max_price: 0, because in their own comment "LLMs frequently fill optional price parameters with 0 when the user did not mention a budget" — and a zero maximum silently returns nothing.
  • Blank entities are stripped, because the embedding endpoint 400s on empty input.

The one lesson to take from this repo

Let the LLM propose a structured query, then validate it in ordinary code before it touches the database. Every hard-won fix in this file is a guard against a plausible-looking value the model made up.

The catalog service then does the search: embed the text, cosine-search Milvus, keep the top-k above a 0.5 similarity threshold, apply price filters to that window, then filter by category. With an image attached it searches text and image collections concurrently and merges by score, and skips category filtering entirely — image similarity is trusted as the better signal.

The Cart agent — where the real engineering is

At 807 lines it is the biggest file, and almost none of that is prompting. The problem it solves: the user says "add the second one", and the cart needs an exact catalog row.

  • Six tool schemas — add, bulk add, remove, bulk remove, view, total.
  • _resolve_catalog_match() is a four-stage name resolver: exact normalised match, then substring containment, then Jaccard token overlap, and only then the top embedding hit if it clears 0.5. Their comment explains why embeddings alone fail: "distinctive product names are systematically underrated by similarity against full descriptions."
  • Prices are pulled out with a regex and cached per cart line, so totals are summed in Python, never by the LLM — "LLMs are unreliable for arithmetic."
  • Pronouns — it, this, both, those — are matched by regex against the last products shown, not sent to the model.

The Chatter — the grounding layer

It never sees raw state. It is handed a hand-built, labelled block:

USER QUERY: ...
PRECEDING AGENT (ran this turn before you): cart | retriever | none
PRECEDING AGENT RESULT (verbatim, authoritative for this turn): ...
CURRENT CART (authoritative): - 1 x Midnight Velvet Blazer @ $89.00
AVAILABLE CATALOG (fresh this turn; the only NEW products you may name): ...
RECENT DISCUSSION (reference only; NOT authoritative for cart state): ...

Every field is ranked by trustworthiness, and the system prompt enforces the ranking:

NEVER SELF-EXECUTE CART ACTIONS. … You may only state that an item was added when PRECEDING AGENT is cart AND the result explicitly confirms it — even if RECENT DISCUSSION contains such phrases.

That rule exists because a summarised history containing "I've added the blazer to your cart" will otherwise make the model claim it did so again. It is the classic multi-turn hallucination in shopping assistants, and the fix is structural: separate authoritative fields from reference fields, and say so in the prompt.

The chatter is the only streaming agent. It emits two message types over Server-Sent Events:

{"type": "images",  "payload": {"Product Name": "/images/x.jpg"}, "timestamp": …}
{"type": "content", "payload": "token", "timestamp": …}
data: [DONE]

That is precisely the protocol mock-server/server.js already reimplements, which is why the NVIDIA UI in ui/ runs against our mock backend unmodified.

The Summarizer — memory hygiene

Only fires past 16,384 characters. Its prompt forbids dropping product facts — "NEVER remove or shorten product specifications, even to save space" — while allowing greetings and filler to be compressed. Note the ordering: summarise, then persist, so what is stored is what the next turn will see.

Guardrails — the part that is nearly empty

150 lines wrapping NeMo Guardrails. Input and output are each checked by asking a rails LLM to regenerate the message; if what comes back is byte-identical to what went in, it is judged safe. On any exception it defaults to safe. The refusal is a single canned string from config.

A6 What one query actually costs

For "show me dresses under $100":

StepWork
memory_node2 HTTP GETs — context, cart
rails_input_node1 LLM call — in parallel with the planner
planner_node1 LLM call → retriever
retriever_node1 LLM call (extraction) + 1 embedding call + 1 Milvus search
chatter_node1 streaming LLM call
rails_output_node1 LLM call
summarize_node0 or 1 LLM call + 1 HTTP POST

Five to seven model calls per user message. Every step is timed into state.timings and exposed at /query/timing — a detail worth copying, since our evaluation chapter will need latency numbers.

Part B

The review

Should RobotEshop build this?

B1 Short answer

Recommendation

Copy the architecture. Do not copy the infrastructure.

The five-agent shape — router, then specialist, then grounded responder, with memory and a validation layer — is sound, well-tested, and directly applicable to the proposal. It is also implementable in a semester by four students.

The stack underneath it — 4×H100 GPUs, three self-hosted NIM models, Milvus with etcd and MinIO, a NeMo Guardrails container — is not something to take on. It contradicts our own proposal, which specifies PostgreSQL, Django/FastAPI and React; it costs more than a student project can carry; and it is orthogonal to what we are graded on.

B2 What we already have

We are further along than the proposal implies. Mapping our repo onto theirs:

Worth saying plainly: mock-server/server.js is already a rule-based implementation of the same architecture. Look at what is in it — intent regexes for cart, compare, tutorials, explain and greeting; a filter parser; a scorer; a glossary; per-user carts. That is a planner, a retriever, a cart agent and a chatter, written without an LLM. The migration path is to replace those rules one at a time with model calls, not to start over.

B3 What to drop, and why

Milvus + etcd + MinIOdropThree containers to run one index. pgvector is one extension on the database the proposal already names

B4 What to keep — the eight ideas that matter

  1. A cheap router in front of expensive specialists. One classification call is far cheaper than giving one mega-prompt every tool.
  2. Extract a structured query with the LLM, then validate it in code. This is what will keep our ROS-version and age-range filters honest.
  3. A per-turn allowlist of retrievable items. We need this more than they do — an invented spec ("yes, it supports ROS 2") on a Rs 500,000 purchase is a real harm, and the proposal's whole premise in §10 is that general chatbots get robot facts wrong.
  4. Label input fields by trustworthiness — authoritative versus reference. The cheapest hallucination fix in the repo.
  5. Never let the model do arithmetic. Totals, price comparisons, "cheapest of these three" — compute in SQL and hand over the answer.
  6. Fail soft, always. Every LLM call in their code has a fallback path. Our demo will run on university wifi in front of an FAC panel.
  7. Summarise memory rather than replaying it, and keep specifications intact when doing so.
  8. Time every stage into the response. We will need those numbers for the testing chapter in Month 7.

B5 Where our domain differs — and needs more than they built

This is the part to raise in the review, because it is where the project earns its own marks rather than reimplementing NVIDIA's.

The core difference

Apparel search is a similarity problem. Robot search is a constraint problem.

"A summer dress" is fuzzy, and embeddings are exactly right for it. But our objectives are almost entirely hard constraints:

age-based and skill-based recommendations … supported platforms and programming tools … the operating system supported … price comparison

"Which robots support ROS 2, run on Raspberry Pi, suit a 12-year-old, and cost under Rs 50,000" is a WHERE clause, not a cosine distance. Embeddings will happily return a ROS 1 robot that reads similar. So our retriever should be hybrid: the LLM extracts a structured filter, SQL applies it exactly, and embeddings only rank what survives — or handle the genuinely vague part of a query, like "something for a school robotics club."

That inversion — SQL as the authority, vectors as the ranker — is the main architectural change I would make against their design, and it happens to fit the PostgreSQL choice already in the proposal.

Two agents they do not have, that our proposal explicitly promises:

  • A comparison agent (§4 "search, filter, and compare"; §9 "advanced comparison tools") — builds a spec-by-spec table across two to four robots. Must be deterministic; a hallucinated comparison table is worse than none.
  • A tutorial and explainer agent (§10 on missing video tutorials, and the jargon problem in the abstract) — answers "what does 6-DOF mean?" from a curated glossary, and surfaces tutorials from the tutorial_count field the scraper already collects.

Both already exist as rules in mock-server/server.js. They are the natural next two nodes on the graph.

One data-integrity problem they never face: their catalog is one CSV they own. Ours is scraped from third parties and goes stale. Verified-seller and price claims need a last_scraped_at timestamp surfaced in the UI, and the assistant should be told when data is old. The proposal sells trust — verified sellers, local availability — and stale prices undermine exactly that.

B8 Open questions for the team

  1. Cart or saved list? Aggregator with affiliate hand-off to Robo.pk, or actual checkout? This decides whether the cart agent is 800 lines or 80.
  2. How many sources at launch? scraper/config.yaml records that IndusRoboTix exposed only 4 products through its API, and roboticspk.com is a parked page. Robo.pk's 144 products may be most of the realistic catalog. That is a defensible scope — but we should say it before the panel asks.
  3. Which hosted LLM, and who pays? Needs deciding before Month 3, with a fallback if credits run out mid-semester.
  4. Image search — in or out? Recommend out for v1. The most expensive thing in the blueprint and the least relevant to robots.
  5. Refresh cadence? How often does the scraper re-run, and how is staleness shown in the UI?

Verdict

Build the same shape: a planner routing to specialists, a grounded responder that can only speak about what this turn actually retrieved, memory in PostgreSQL, and LLM output validated by ordinary code before it reaches the database.

Do not build the same system: no GPUs, no Milvus, no NeMo Guardrails, and no apparel-shaped assumption that similarity search alone can answer "which robots support ROS 2". For robots, SQL is the authority and embeddings are the ranker — and that inversion, plus the compare and explain agents, is where RobotEshop is genuinely a different project rather than a re-skin of the blueprint.
